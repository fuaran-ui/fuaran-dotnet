# Phase 2026 — the op-stream escapers onto Core's `Json.escapeInto`: before and after

Host: Intel Core i7-8650U (Intel64 Family 6 Model 142 Stepping 10, 8 logical processors), Windows 11
(10.0.26300), .NET SDK 10.0.203, node 22.20.0, Fable 5.0.0. This is **not** the reference host the committed
`op-append-baseline.json` was captured on (Family 6 Model 204, 16lp), so these readings are a before/after pair
on one machine and are deliberately not folded into that artifact; the escape metrics are declared in the op
catalogue, and the next reference-host `capture op` fills them.

"Before" is the tree at the phase's base with only the harness added (`EscapeRate.fs`, `escape-node/`), run before
any escaper was changed; "after" is the same harness over the collapsed tree. Every run printed the same encoded
length per case (clean 4,169, heavy 7,241, keys 3,436 characters), so both sides encoded the same bytes.

## `escape-rate 20000` (.NET, Release, in-process), two runs each side

| case | before mean | before alloc | after mean | after alloc |
|---|---|---|---|---|
| clean (4,096 characters, nothing to escape) | 48.1 / 45.7 µs | 26,376 B | 36.8 / 32.3 µs | 26,376 B |
| heavy (4,096 characters, every fourth escaped) | 194.7 / 225.4 µs | 130,824 B | 52.3 / 50.8 µs | 32,520 B |
| keys (256 short keys and values) | 198.0 / 190.2 µs | 108,992 B | 190.5 / 196.4 µs | 108,992 B |

`keys` did not move beyond noise: its strings are two to four characters long with nothing to escape, so the old
per-character loop was already cheap there and the case's cost is the object writer's per-member work (the sort,
the closures), which this phase does not touch.

## `OpStreamBenchmarks` (BenchmarkDotNet `--inProcess`, one run each side)

The out-of-process toolchain timed out generating its boilerplate on this host (BenchmarkDotNet's two-minute build
limit), so both sides ran in-process. Its error bars on this machine are wide (up to ±20%); read the allocation
column first.

| benchmark | before mean | after mean | alloc (both) |
|---|---|---|---|
| EncodeOp UpdateProp | 1.821 µs | 0.956 µs | 1.6 KB |
| EncodeOp InsertChild | 5.635 µs | 5.146 µs | 4.98 KB |
| EncodeOp Batch16 | 30.925 µs | 26.662 µs | 23.02 KB |
| ComputeHash UpdateProp | 13.490 µs | 11.981 µs | 8.53 KB |
| ComputeHash InsertChild | 18.458 µs | 15.293 µs | 12.45 KB |
| ComputeHash Batch16 | 73.050 µs | 58.708 µs | 45.55 KB |

The corpus ops carry short clean strings, so allocation is unchanged and only `EncodeOp UpdateProp` moves by more
than the run's own scatter.
